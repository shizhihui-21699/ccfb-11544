# 压测与参数调优

记录用 `replay` 对 `rlproxy` 压测得到的真实数据、踩到的坑，以及据此确定
参数的方法。所有数字来自本机（Apple Silicon, macOS）回环压测，绝对值会
随机器变化，重点看**方法和相对关系**。

## 1. 测量方法

- 上游用事件驱动的 `upstream_echo`，单进程承载全部连接，避免压测瓶颈
  出在被测对象之外。
- 攻击流量与正常流量分两个统计组，各自带独立网段的源 IP；正常客户端
  带稳定用户令牌。这样能分别回答两个问题：攻击被拦住了吗？正常用户受
  影响了吗？
- 每组输出 `sent / allowed / 放行率 / 429 / IO 错误` 和
  `p50/p90/p95/p99/max` 延迟。
- 连接建立按每 100ms 最多 200 条节流，模拟真实 ramp-up，避免一次性
  打满监听半连接队列（那测的是 TCP 栈不是限流器）。

## 2. 关键结果

### 混合攻击（400 攻击连接 + 30 正常连接，8 秒）

| 组 | 发送 | 放行 | 放行率 | 429 | IO 错误 | p50 | p99 |
|---|---|---|---|---|---|---|---|
| 正常 | 2215 | 2209 | **99.73%** | 6 | 0 | 40ms | 126ms |
| 攻击 | 15800 | 592 | **3.75%** | 15208 | 0 | 28ms | 94ms |

结论：攻击流量 96% 以上在限流层被 429 挡掉，正常流量近乎全通，且全程
零 IO 错误、无 fd 泄漏。被放行的少量攻击请求受限于令牌桶的持续补充速率，
属于预期——限流器把攻击压制到后端能承受的稳态，而不是追求 0 放行。

### 纯正常固定速率（500 rps，5 秒）

放行率 99.4%，p99=32ms。出现的少量 429 是**路由聚合桶 + 每 IP 桶在
新连接身份下的瞬时叠加**，不是过载（CPU、连接数都远未到顶）。把
`route_api` 的 burst 从 4000 提到 8000、或把每 IP `rate` 从 30/s 提到
50/s 后该现象消失。

### slowloris（150 连接，每 2s 滴 1 字节，目标占 12s）

150 条慢速连接全部被 `head_timeout_ms=8000` 主动回收，统计
`active=0`，没有连接堆积。慢速攻击的防御不依赖限流算法，而依赖请求头
超时——这是单独的一道闸。

## 3. 踩过的坑（都已修）

### 3.1 kqueue 边沿触发 + EV_DISABLE 丢事件

最初 kqueue 后端用 `EV_CLEAR`（边沿触发），并在关闭写事件时对 filter
`EV_DISABLE`、需要时再 `EV_ENABLE`。边沿信号在 disable 期间不会重投，
导致监听 fd 的读事件被永久静音——表现为代理起来了但 `conns=0`、curl
连上后无响应。

**修法**：两个后端统一改成水平触发（kqueue 去掉 `EV_CLEAR`，epoll 去掉
`EPOLLET`）。水平触发下只要 fd 就绪就持续通知，interest 开关不会丢事件，
语义在 kqueue/epoll 间完全一致，代价是少量多余唤醒（LT 本就可接受）。

### 3.2 匿名限流用了一个全局 `anon` key

最早把无令牌请求归到单个 `anon_quota` 桶（10/s）。结果所有匿名调用者
**共用一个 key**，一个人刷就能把全局限额耗光，其他匿名用户全部 429——
限流器本身成了单点瓶颈，压测里正常组放行率掉到 0。

**修法**：匿名配额改成按 IP 维度（`type=ip key=$ip`），让限流身份和
来源绑定。原则：**共享 key 的 zone 一定是有意的聚合总量控制，不能用来
限制彼此无关的用户群。**

### 3.3 监听 backlog 被系统静默截断

macOS `kern.ipc.somaxconn` 默认只有 128，`listen(fd, 4096)` 会被截到
128。高并发建连时半连接队列溢出，回放侧出现大量 connect 失败（被记成
IO 错误）。

**修法**：backlog 提到 16384；Linux 下启动时读
`/proc/sys/net/core/somaxconn` 自适应。回放在客户端侧再加建连节流。
生产 Linux 还应 `sysctl net.core.somaxconn=16384`、
`net.ipv4.tcp_max_syn_backlog` 同步调大。

### 3.4 滑动窗口边界 off-by-one

窗口淘汰条件最初写成 `ts <= now-window`，把“恰好等于窗口年龄”的时间戳
也淘汰了，导致边界处多放行一个请求。正确语义是半开区间
`(now-window, now]`，淘汰条件应为 `ts < now-window`。单元测试用假时钟
锁定了这个边界。

## 4. 怎么按压测结果调参数

按从外到内的顺序，每层单独压、单独看计数器（`kill -USR1 <pid>`）：

1. **先定路由聚合层容量**。用无攻击的固定 rps 回放（`-M replay -r N`），
   从后端能稳定承受的 rps 反推 `route_api` 的 `rate`，`burst` 设成
   rate 的 2 倍吸收秒级抖动。这层是后端的总闸。
2. **再定每 IP 层**。用单源 burst 压，确认突发被压到稳态速率且
   Retry-After 合理。`rate` 取“单个正常客户端的合理峰值”，`burst`
   一般是 rate 的 1.5–2 倍。burst 给太大等于变相放开，给太小会误伤
   正常的瞬时并发（一个页面同时发十几个请求）。
3. **令牌层按业务配额定**。登录用户用滑动窗口日志给精确的每分钟配额，
   避免令牌桶允许把整分钟额度在第一秒打完。
4. **敏感路由单独硬顶**。`/admin` 这类用滑动窗口给很小的精确上限。
5. **看 p99 而不是平均值**。限流误伤通常表现为正常组出现零星 429 或
   p99 抖动，平均值会掩盖。目标是正常组放行率 ≥99.5% 且 429 仅出现在
   攻击组。
6. **每次只改一个参数**，热加载（改文件等 mtime 检测，或 SIGHUP）后
   重放同一模型对比，计数器能直接告诉你是哪一层在拒绝。

### 算法选择经验

- 需要**突发容忍 + 长期稳态**（IP 层、路由总量）→ 令牌桶。
- 需要**精确硬上限、防止额度囤积**（用户配额、敏感路由）→ 滑动窗口日志。
- 滑动窗口的内存是 O(rate)，单 key rate 别配到十万以上（配置里已加
  100000 上限）；超高吞吐的聚合限制用令牌桶。

## 5. 上线前的系统参数（Linux）

```
net.core.somaxconn = 16384
net.ipv4.tcp_max_syn_backlog = 16384
net.ipv4.ip_local_port_range = 1024 65535
fs.file-max / ulimit -n     # 至少 > max_conns 的两倍
```
